# TECHNICAL_PLAN.md 技术审核：主要问题、风险与建议

审核对象：[TECHNICAL_PLAN.md](./TECHNICAL_PLAN.md)  
日期：2026-11-11  
硬件前提：GUITION JC3636W518C，ESP32-S3（240MHz 双核）、16MB Flash、8MB PSRAM。  
说明：以下结论基于文档和现有 `PianoTimer/` 代码的静读，未做板端实测。其中的算力数字是估算，需要用实际测量复核。

## 1. 总体结论

方案设计合理，取舍克制。近期目标"可靠统计有效弹琴时间"在 ESP32-S3 上可行。"逐音符的琴谱比对与错音反馈"不适合完全放在板端，应以 Mac/手机承担为主，文档阶段 F 已留有这个方向。

## 2. 可行性评估

| 模块 | 结论 | 说明 |
| --- | --- | --- |
| 16/24kHz 持续采音、环形缓冲 | 可行 | 数据量约 32–48 KB/s。 |
| 多分辨率 FFT（1024/4096 点） | 可行，需实测 | 按 16ms 一帧，4096 点 FFT 每秒约 62 次，估计占单核 10% 量级。 |
| 4kHz 降采样低音分支 | 可行 | 需自行实现抗混叠滤波（多相/半带）。 |
| 模板匹配、简单 NNLS | 可行 | 在对数频率轴加稀疏模板上做，计算量小；在 2048 个线性频点上迭代则偏重。 |
| 小型 CNN 声音分类（int8） | 可行 | 可用 ESP-NN/TFLM 或 ESP-DL，模型需很小。 |
| 板端完整跟谱、逐音符纠错 | 风险高 | 瓶颈是精度和数据，不是算力。 |

## 3. 主要问题与风险

### P1：板端"音符识别"的精度被高估

- 低音区（A0–C2）基频很弱，常只剩泛音；多数 MEMS 麦克风在 60Hz 以下已衰减。
- 24kHz、4096 点窗口的频率分辨率约 5.9Hz，大致 A3 以上才能分辨半音。
- 4kHz 降采样的 1 秒窗口分辨率约 1Hz，而 A0 一个半音仅约 1.6Hz，加窗后主瓣约 2Hz，仅勉强可分。
- 和弦、踏板共鸣下的单麦克风多音高识别本身就很难做到高准确率。

建议：

- 把"计时（板端）"和"错音/节奏反馈（Mac/手机优先）"拆成两个独立目标。
- 两者不共用验收指标，计时也不依赖后者。

### P1：低音确认延迟与 1 秒计时规则的交互需要写明

低音分支需要约 1 秒窗口，而计时的关键阈值也是 1 秒。文档用"起音候选 → 确认 → 回填"处理，思路正确，但还需明确：

- 候选被拒绝时如何回滚。
- UI 累计值是否允许回退（建议写成硬约束：只增不减）。
- 回填区间的最大长度，避免状态无限等待。

### P2：噪声底"冻结"可能死锁

文档规定"可信琴声期间冻结背景更新"。若分类器把持续的风扇声误判为琴声，噪声底永远不会更新，误判会持续。

建议：

- 设置冻结最长时长。
- 超时后强制慢速更新。
- 用分类器的不确定度作为解除条件。

### P2：频漂补偿有自举风险

用检测结果更新模板，再用模板做检测，可能漂向错误音高。文档已有限幅与冻结。

建议：

- 只在孤立音、多次一致时更新。
- 始终保留"恢复默认"。

### P2：88 路 Goertzel 的算力并不是问题

- 每秒约 141 万次递推，只占 240MHz 的 1–3%（估算）。
- 真正的约束是各音所需的窗口长度。可以让每个音符使用与其频率匹配的窗长（类似 CQT 的滤波组）：低音长窗、高音短窗。
- 建议把它加入阶段 B 的 Mac 离线对照，与三组 FFT 方案比较精度与资源。

### P2：声音分类的数据量是最大的不确定性

- 现有录音不足以证明人声排除能力（文档第 14 节已承认）。
- 哼唱和轻声钢琴都有明显音高，是最难区分的组合。
- "钢琴与人声同时存在"的多标签识别对小模型难度更高。

建议：

- 用公开的钢琴数据集（如 MAESTRO、MAPS）与人声、环境音数据集预训练，再用板子自己录的数据微调。
- 第一版先做"是否包含钢琴"，人声标签作为后续目标。

### P3：文档未覆盖的工程项

1. **累计时间掉电保护**：周期性落盘（如每分钟），NVS 写入要合并，避免磨损 Flash。
2. **提示音自激**：若扬声器会发声，分析期间需静音，否则污染输入。
3. **增益与削波**：I2S 麦克风通常没有 AGC，需要固定增益并检测削波。
4. **内存位置**：
   - FFT 工作区放内部 SRAM。
   - 长缓冲放 PSRAM。
   - LVGL 刷屏与 PSRAM 访问会争带宽，`PianoTimer/lvgl_port_v8.h` 中也有提示。
5. **模型存放**：放入独立 Flash 分区并内存映射，避免复制到 RAM。
6. **隐私**：麦克风常开并保存原始录音，需要明确的开关和界面提示。
7. **步长偏密**：4096 点窗口配 16ms 步长，重叠约 90%，大量冗余。可改为短窗 16ms、中窗 32–64ms、低音分支 128–256ms，计算量可降低数倍。
8. **16kHz 与 24kHz**：钢琴最高基频约 4.2kHz，16kHz 采样对计时已足够。建议默认 16kHz，24kHz 作为对照实验。

## 4. 与现有代码的对应

- [OfflineRecorder.h](./PianoTimer/OfflineRecorder.h) 把录音放在 PSRAM，没有写 Flash，不会遇到 Flash 擦写暂停缓存的问题。
- 文档第 11 节写了"录音写 Flash"。若将来要在持续采集时写 Flash：
  - 擦除期间对 Flash 和 PSRAM 的访问会暂停。
  - 此时 I2S 中断和采集缓冲必须在内部 SRAM，中断要 IRAM 安全。
  - 缓冲要覆盖最长擦写停顿（几十到几百毫秒）。
- 16MB Flash 存 16kHz 16bit WAV（约 32 KB/s）只能存几分钟。长期数据采集建议通过串口/WiFi 传到 Mac，或使用 TF 卡（需确认板子是否带）。

## 5. 建议的下一步

1. 保持"先 A、B 阶段，再决定是否上板"的顺序。
2. 阶段 B 增加"板端预算"一栏：每种方法在 Mac 上的运算量，换算成 S3 每秒的周期数，再用实测复核。
3. 在文档中拆分"计时（板端）"与"琴谱比对（Mac/手机优先）"两个目标。
4. 补充"噪声底冻结超时"、"频漂更新条件"、"累计时间落盘"。
5. 把 Goertzel/CQT 式滤波组加入阶段 B 的对照实验。
